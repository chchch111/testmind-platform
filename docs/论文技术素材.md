# 基于RAG与思维导图的智能测试用例自动生成与管理平台论文技术素材

## 一、系统总体架构

本系统采用前后端分离架构，后端基于 Python FastAPI 实现业务接口，业务数据使用 MySQL 持久化存储，知识库向量检索采用 LangChain、bge-small-zh 与 FAISS 实现，大模型推理部分调用 DeepSeek-v4-flash 云端 API。

系统整体属于混合式 AI 架构：Embedding 向量化计算和 FAISS 向量检索部署在自有应用服务端内部运行，不调用第三方 Embedding API，也不依赖第三方向量数据库服务；大模型推理能力通过 DeepSeek-v4-flash 云端 API 提供。该架构兼顾了知识库数据可控性、部署成本和大模型生成效果。

## 二、核心模块划分

系统后端主要包括以下模块：

1. 用户与权限基础模块：保存用户信息，为用例创建人、更新人、测试任务执行人提供数据关联。
2. 思维导图用例管理模块：通过 test_case_sets 和 test_case_nodes 两张表保存用例集和树形节点，使用 parent_id 表示思维导图父子关系。
3. 用例版本管理模块：每次创建、修改、回退或删除节点时，向 test_case_node_versions 表写入版本快照，实现历史追溯和版本回退。
4. XMind 导入导出模块：支持解析新版 .xmind 文件中的 content.json，将主题结构导入为数据库树形节点；同时支持将数据库中的用例树重新导出为 .xmind 文件。
5. 测试任务模块：支持创建测试任务、绑定用例集、分配执行人，并为执行人自动生成测试执行记录。
6. 执行同步模块：执行人可同步任务和执行记录，并提交通过、失败、阻塞等执行状态；系统通过 sync_version 和 sync_status 辅助处理同步冲突。
7. RAG 知识库模块：支持创建知识库、添加知识来源、文本切片、向量化、FAISS 持久化索引构建和相似文本检索。
8. AI 自动生成模块：根据用户测试需求，先通过 RAG 检索相似历史知识，再调用 DeepSeek-v4-flash 生成结构化思维导图测试用例，并保存为用例集。

## 三、RAG 工作流程

系统的 RAG 流程如下：

1. 用户上传或录入知识来源，包括 XMind 测试用例、硬件测试规范、历史测试文档和手动文本。
2. 后端读取原始文本内容。
3. 使用 LangChain RecursiveCharacterTextSplitter 对文本进行切片。
4. 使用 bge-small-zh 在应用服务端内部生成文本向量。
5. 使用 FAISS 构建向量索引，并将 index.faiss 文件持久化保存到磁盘。
6. 使用 docstore.json 保存 FAISS 向量位置与 MySQL 知识切片 ID 的映射关系。
7. MySQL 保存知识库、知识来源、知识切片、FAISS 索引路径和元数据。
8. 用户输入新的测试需求。
9. 系统将测试需求向量化，在 FAISS 中检索相似知识切片。
10. 后端将检索上下文和用户需求拼接为 Prompt。
11. 调用 DeepSeek-v4-flash 云端 API 生成结构化测试用例。
12. 解析生成结果并保存为思维导图用例树。

## 四、AI 生成约束设计

系统在调用大模型时增加系统提示词约束：

1. 禁止输出思考过程。
2. 禁止输出推理草稿。
3. 禁止输出 <reasoning> 标签内容。
4. 只输出最终结构化测试用例结果。
5. 输出必须是合法 JSON。
6. JSON 顶层必须包含 case_set_name 和 nodes。

该设计可以降低大模型输出不可解析内容的概率，使生成结果更容易自动保存到数据库并转化为思维导图结构。

## 五、数据库设计说明

系统使用 MySQL 保存结构化业务数据，主要数据表包括：

1. users：用户信息表。
2. test_case_sets：测试用例集表。
3. test_case_nodes：思维导图用例节点表。
4. test_case_node_versions：用例节点历史版本表。
5. xmind_files：XMind 文件导入导出记录表。
6. xmind_import_batches：XMind 导入批次表。
7. test_tasks：测试任务表。
8. test_task_case_sets：任务与用例集关联表。
9. test_task_assignees：任务执行人表。
10. test_execution_records：测试执行记录表。
11. knowledge_bases：RAG 知识库表。
12. knowledge_sources：知识来源表。
13. knowledge_chunks：知识切片表。
14. faiss_indexes：FAISS 索引记录表。
15. rag_retrieval_records：RAG 检索记录表。
16. ai_generation_records：AI 生成记录表。

其中，FAISS 保存向量索引文件，MySQL 保存切片文本、来源信息、索引路径和业务关联元数据。系统没有直接依赖 FAISS 内部向量顺序作为业务主键，而是通过 docstore.json 和 chunk_id 建立稳定映射，降低索引重建带来的关联风险。

## 六、系统创新点

1. 面向硬件测试场景的思维导图式用例管理：系统使用树形结构组织测试用例，更符合硬件测试中“产品—模块—功能—场景—用例”的分层管理方式。
2. 服务端本地化向量检索与云端大模型推理结合：Embedding 与 FAISS 检索在自有服务端运行，保证知识库数据可控；大模型推理调用云端 API，提升生成质量。
3. 基于 RAG 的历史知识复用：系统不是直接让大模型凭空生成用例，而是先检索历史用例和硬件测试规范，再结合用户需求生成结果，提高生成内容与实际测试场景的相关性。
4. XMind 导入导出闭环：系统支持将已有 XMind 文件导入平台，也支持将平台用例树导出为 XMind 文件，便于和传统测试文档流程衔接。
5. 用例版本追溯与回退：系统保存用例节点历史版本，支持回退到历史版本，提高测试资产管理的安全性和可追溯性。
6. 测试任务下发与执行同步：系统支持将用例集绑定到测试任务，并下发给执行人，执行人可同步任务并更新执行状态。

## 七、系统局限性

1. AI 自动生成模块依赖外网访问 DeepSeek API，断网或云端接口不可用时，自动生成功能不可用。
2. FAISS 以文件形式保存向量索引，适合中小规模知识库；在海量数据和分布式多实例部署场景下，需要额外设计索引同步机制。
3. FAISS 文件型索引不天然支持多服务实例共享，如果云服务器部署多副本，需要共享存储或重建索引策略。
4. 知识库文本切片和向量构建会占用一定 CPU 和内存，知识库规模较大时需要优化批处理和索引构建流程。
5. XMind 导入目前主要支持包含 content.json 的新版 .xmind 格式，对老旧版本或非标准 XMind 文件兼容性有限。
6. 系统状态字段主要由后端代码约束，数据库层使用 VARCHAR 保留扩展性，但需要后端持续做好参数校验。
7. 当前系统以单机可用为目标，尚未实现复杂权限体系、审计日志、对象存储和分布式任务队列。

## 八、实验与联调结果

当前系统已完成端到端联调，关键结果如下：

1. FastAPI 健康检查通过。
2. MySQL 数据库连接通过。
3. 思维导图用例 CRUD、版本记录和回退通过。
4. XMind 导入导出通过。
5. 测试任务创建、下发、执行同步通过。
6. LangChain + bge-small-zh + FAISS 知识库构建和检索通过。
7. DeepSeek-v4-flash AI 自动生成测试用例通过。
8. AI 生成结果已成功保存为数据库用例树，并可导出为 XMind 文件。

当前实际配置的 Embedding 模型为 BAAI/bge-small-zh-v1.5，实测向量维度为 512 维。系统在 faiss_indexes 表中记录实际向量维度，避免模型版本变化导致论文与实验结果不一致。

## 九、系统部署与运行环境

系统已完成真实云服务器部署（腾讯云 CVM，Ubuntu 22.04，2 核 2GB 内存），采用前后端分离架构：前端为 Vue 构建的静态资源，由 Nginx 托管并监听 8080 端口；后端 FastAPI 由 systemd 服务守护常驻，监听本机 8011；Nginx 作为反向代理统一转发 `/api` 请求，从而避免跨域并隐藏后端端口。MySQL 8.0 持久化业务数据，FAISS 索引与 bge-small-zh 模型缓存保存在服务器磁盘 `storage/` 目录。

部署过程验证了以下结论：

1. 系统可运行于 2 核 / 2GB 内存的入门级 CPU 云服务器，无需 GPU 资源；Embedding 向量化与 FAISS 检索在服务端本地运行，知识库数据可控。
2. 大模型推理仅依赖 DeepSeek 云端 API，服务器需可访问外网，但本地无需高性能算力，部署成本可控。
3. 服务通过 systemd 守护，支持开机自启与崩溃自动拉起；Nginx 托管静态资源并反代 API，实现了前后端同源部署。
4. 部署过程中发现并解决了宝塔面板残留配置导致的 MySQL 启动失败、torch 与 transformers 在 Python 3.11 上的兼容性问题等实际工程问题，体现了系统在真实环境中的可部署性。
