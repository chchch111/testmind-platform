## 一、部署架构

```
浏览器访问  http://IP:8080
        │
        ▼
   Nginx (8080)  ── 托管前端 dist 静态文件 + /api 反向代理
        │ proxy_pass http://127.0.0.1:8011
        ▼
   uvicorn (FastAPI, 8011)  ── systemd 守护常驻
        │
        ├─ MySQL 8.0 (127.0.0.1:3306)  业务数据持久化
        └─ storage/ 目录
             ├─ faiss/      FAISS 向量索引文件
             ├─ uploads/    XMind/文档上传
             ├─ exports/    XMind 导出
             └─ models/     bge-small-zh 模型缓存
```

要点：
- 前端是 Vue 构建产物（静态文件），由 Nginx 托管，不需要 Node 运行时。
- 后端 FastAPI 用 uvicorn 监听 0.0.0.0:8011，但只允许本机（127.0.0.1）经 Nginx 访问，不直接暴露公网。
- 前端 request.js 的 baseURL 为空字符串，所有 `/api/*` 请求同源发到 8080，由 Nginx 转发给后端，天然规避跨域。

## 三、环境安装步骤

### 3.1 系统基础

```bash
sudo apt update && sudo apt upgrade -y
sudo apt install -y git curl wget unzip build-essential python3-venv python3-pip
```

### 3.2 Python

Ubuntu 22.04 默认 Python 3.10，项目使用 3.11 构建虚拟环境：

```bash
sudo apt install -y python3.11 python3.11-venv python3.11-dev
```

### 3.3 MySQL

```bash
sudo apt install -y mysql-server
```

**部署坑 1：宝塔面板残留配置导致 MySQL 无法启动**
- 现象：`mysqld` 启动失败，错误 `unknown variable 'query_cache_size=16M'` 和 `Failed to find valid data directory`。
- 原因：服务器此前安装过宝塔面板，其遗留的 `/etc/my.cnf` 指向宝塔数据目录 `/www/server/data`，且包含 MySQL 8.0 已移除的 `query_cache_size` 参数，导致新装的 MySQL 8.0 崩溃。
- 解决：备份并移除宝塔配置，清空 `/var/lib/mysql` 后重新初始化：

```bash
sudo mv /etc/my.cnf /etc/my.cnf.bak_baota
sudo rm -rf /var/lib/mysql
sudo mkdir -p /var/lib/mysql /var/run/mysqld
sudo chown -R mysql:mysql /var/lib/mysql /var/run/mysqld
sudo mysqld --initialize-insecure --user=mysql
sudo systemctl start mysql
```

- 设置 root 密码后验证连接。

### 3.4 Nginx

```bash
sudo apt install -y nginx
```

**部署坑 2：宝塔版 Nginx 与 systemd 版冲突**
- 现象：apt 安装后 `systemctl status nginx` 显示 failed，且 80 端口被一个旧进程占用。
- 原因：宝塔自带一套 Nginx（`/www/server/nginx/sbin/nginx`），占用 80 端口并读取宝塔自有配置目录，新装的 systemd 版 Nginx 无法绑定端口。
- 解决：停掉宝塔 Nginx 进程，改用 systemd 管理标准 Nginx；本项目 Nginx 监听 8080，与宝塔的 80 端口错开，最终确认宝塔数据不需要后一并清理。

### 3.5 Python 依赖与版本适配

```bash
python3.11 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
```

**部署坑 3：torch 与 transformers 在 Python 3.11 上的兼容 bug**
- 现象：`import sentence_transformers` 报错 `ValueError: Duplicate dispatch rule for <built-in function intern>`，堆栈指向 torch._dynamo 的 polyfills。
- 根因：默认安装的 torch 2.13.0 拉取了一整套 nvidia-cuda 依赖；其 `_dynamo` 模块与 transformers 4.57.6 的 flex_attention 在 Python 3.11 上存在已知冲突。本机 Windows/Python 3.13 上未触发，服务器 Python 3.11 触发。
- 解决（两步，最终定位为 transformers 版本问题）：

```bash
# 1) 换用 CPU 版 torch，避免无用 CUDA 依赖
pip uninstall -y torch
pip install torch==2.12.1 --index-url https://download.pytorch.org/whl/cpu

# 2) 关键：降 transformers 版本，绕开 flex_attention 的 bug
pip install "transformers==4.48.3"
```

- 验证：`python -c "import torch; import sentence_transformers"` 通过。

## 六、Nginx 配置

```
server {
    listen 8080;
    root /opt/testmind/frontend/dist;
    index index.html;

    location / {
        try_files $uri $uri/ /index.html;   # Vue history 路由回退
    }

    location /api/ {
        proxy_pass http://127.0.0.1:8011;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }

    location /health/ {
        proxy_pass http://127.0.0.1:8011;
        proxy_set_header Host $host;
    }
}
```

- `try_files` 回退保证刷新任意前端路由不 404。
- `/api/` 与 `/health/` 反代到后端。

## 七、后端 systemd 常驻

创建 `/etc/systemd/system/testmind.service`：

```ini
[Unit]
Description=TestMind FastAPI Backend
After=network.target mysql.service
Wants=mysql.service

[Service]
Type=simple
User=ubuntu
WorkingDirectory=/opt/testmind/backend
EnvironmentFile=/opt/testmind/backend/.env
ExecStart=/opt/testmind/backend/.venv/bin/python -m uvicorn app.main:app --host 0.0.0.0 --port 8011
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```

启用并验证：

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now testmind
sudo systemctl status testmind
```

优点：开机自启、进程崩溃自动拉起、脱离 SSH 会话独立运行。

## 八、防火墙与安全组

- 腾讯云控制台安全组需放行入站 TCP 8080（前端）与 TCP 8011（后端，验证后可不对外）。
- 服务器本机 ufw 需放行：`sudo ufw allow 8080/tcp`、`sudo ufw allow 8011/tcp`。
- MySQL 3306 仅保持本机回环访问，不对公网开放。

## 九、性能与资源适配

服务器为 1.9GB 内存，为缓解内存压力：

- 重建 2GB swap 交换分区（清掉宝塔残留 swap 后）：
  ```bash
  sudo fallocate -l 2G /swapfile
  sudo chmod 600 /swapfile && sudo mkswap /swapfile && sudo swapon /swapfile
  echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
  ```
- bge-small-zh 模型首次加载占用内存较高，RAG 首次检索会较慢（本机实测约 78 秒），模型缓存后秒回。
- 部署结论（可写入论文）：本系统 Embedding 与 FAISS 检索可运行在 2 核 / 2GB 内存的入门级 CPU 云服务器上，无需 GPU；大模型推理仅调用 DeepSeek 云端 API，因此对本地算力要求低，部署成本可控。

## 十一、可写入论文的部署结论

本系统采用前后端分离架构部署于单台 Ubuntu 22.04 CPU 云服务器：前端由 Nginx 托管静态构建产物，后端 FastAPI 由 systemd 守护，Nginx 作为反向代理统一入口（8080）。Embedding 向量化与 FAISS 检索在服务端本地运行，保证知识库数据可控；大模型推理通过 DeepSeek 云端 API 完成，本地无需 GPU。该方案在 2 核 2GB 内存的入门级云服务器上即可完整运行，部署成本低、结构清晰、易于维护，验证了面向中小规模知识库的测试用例管理平台具备低成本上线的可行性。
